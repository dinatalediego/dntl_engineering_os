# DNTL Engineering OS

A portfolio control plane for engineering repositories: **discover → inspect → score → prioritize → refresh**.

## v0.2 — Automated Engineering Command Center

The dashboard no longer depends on hand-authored repository health. Its primary input is `data/inventory.json`, generated by `scripts/scan-github.mjs` from observable GitHub evidence.

### Closed control loop

```text
GitHub repositories
      ↓
scripts/scan-github.mjs
      ↓
recursive repository evidence
      ↓
Health Score v1
      ↓
data/inventory.json
      ↓
Next.js dashboard + filters
      ↓
intervention queue
```

`.github/workflows/refresh-inventory.yml` runs the loop automatically every day at **08:17 America/Lima** (13:17 UTC), can be run manually with `workflow_dispatch`, and also runs when the scanner, score rules, dashboard or workflow itself changes.

Before committing a refreshed snapshot it must pass:

1. `npm run test:health`
2. `npm run scan:github`
3. `npm run build`

The generated snapshot is committed only after those checks succeed.

## Health Score v1

The score is deliberately explainable and totals 100 points:

| Dimension | Weight | Observable evidence |
|---|---:|---|
| Freshness | 25 | age of last repository push |
| Documentation | 15 | root README |
| Automation | 20 | GitHub Actions workflows |
| Testing | 20 | test directories/config/files anywhere in the tree |
| Operability | 10 | package/runtime manifest, Docker or Vercel/Next config |
| Hygiene | 10 | non-archived, non-empty, no tracked `.env`-like secrets |

Thresholds:

- **80–100:** healthy
- **60–79:** watch
- **0–59:** risk
- **Not scanned:** no score is calculated because evidence is unavailable

Rules live in `config/health-rules.json`; calculation lives in `scripts/health-score.mjs`; deterministic tests live in `scripts/health-score.test.mjs`.

## Dashboard filters

- Search by repository, tag, database or capability
- Health
- System type
- Visibility
- Evidence coverage
- Delivery signal
- Focus mode: risk + watch + unknown observability + visible testing gaps

The dashboard separates **risk** from **lack of observability**. A private repository that cannot be inspected is never assigned an invented low score.

## Private repositories — one-time control-plane credential

GitHub does not let one repository's default `GITHUB_TOKEN` inspect every other private repository owned by the user. For complete private coverage, create a fine-grained GitHub token that can read the required repositories and save it in this repository's Actions secrets as:

```text
DNTL_GITHUB_TOKEN
```

Minimum intended access: repository metadata/contents and Actions metadata read access across the repositories the control plane should govern. The token belongs in GitHub Actions Secrets only; **never commit it**.

Without that secret the scanner intentionally discovers/scores public repositories only and the UI displays the coverage guardrail. Once the secret exists, the next scheduled/manual run expands discovery to owned private repositories automatically.

## Local commands

```bash
npm install
npm run test:health
npm run scan:github
npm run build
npm run dev
```

For a full private scan locally:

```bash
DNTL_GITHUB_TOKEN=... npm run scan:github
```

## Next telemetry layers

Repository health is the first evidence layer, not the final definition of production health. The architecture is ready to add independent adapters for:

- Vercel deployment/build/runtime status
- Supabase migrations, RLS and database health
- ETL execution history and rejected rows
- dependency/contract health between repositories
- secrets/security scanning
- rollback readiness

Those signals should extend the model without overwriting GitHub evidence, so every score remains auditable.
